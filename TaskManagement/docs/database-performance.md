# بررسی عملکرد پایگاه داده و تحلیل اجرای کوئری‌ها

## ۱. هدف آزمایش

هدف این آزمایش بررسی نحوه اجرای یک کوئری واقعی از پایگاه داده Kasbify با استفاده از دستور `EXPLAIN ANALYZE` در PostgreSQL است.

در این آزمایش، تأثیر وجود یک ایندکس ترکیبی روی ستون‌های `store_id` و `due_at` بررسی شده است.

ایندکس مورد بررسی:

```sql
CREATE INDEX tasks_store_id_due_at_index
ON tasks (store_id, due_at);
```

از آنجا که پایگاه داده در زمان آزمایش تنها ۱۰۱ رکورد در جدول `tasks` داشته است، نتایج این آزمایش را نمی‌توان به‌عنوان معیاری برای عملکرد سیستم در مقیاس بزرگ در نظر گرفت. هدف اصلی، آشنایی عملی با Execution Plan و مقایسه رفتار PostgreSQL در دو وضعیت است.

## ۲. کوئری مورد بررسی

کوئری زیر برای یافتن وظایف یک فروشگاه که زمان سررسید آن‌ها گذشته است، استفاده شده است:

```sql
SELECT
    id,
    title,
    status,
    due_at
FROM tasks
WHERE store_id = 1
  AND due_at < NOW()
ORDER BY due_at;
```

این کوئری از دو شرط فیلتر استفاده می‌کند:

- `store_id = 1`: انتخاب وظایف متعلق به فروشگاه مشخص‌شده.
- `due_at < NOW()`: انتخاب وظایفی که زمان سررسید آن‌ها گذشته است.

نتایج نیز بر اساس `due_at` مرتب می‌شوند.

برای تحلیل اجرای کوئری از دستور زیر استفاده شده است:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    id,
    title,
    status,
    due_at
FROM tasks
WHERE store_id = 1
  AND due_at < NOW()
ORDER BY due_at;
```

## ۳. نتایج بدون ایندکس

در مرحله اول، ایندکس ترکیبی مورد بررسی از جدول حذف شد و کوئری اجرا گردید.

خلاصه خروجی:

```text
Sort
  Sort Key: due_at
  Sort Method: quicksort
  Memory: 25kB
  -> Seq Scan on tasks
       Filter: ((store_id = 1) AND (due_at < now()))
       Rows Removed by Filter: 101
       Buffers: shared hit=4

Planning Time: 1.046 ms
Execution Time: 0.036 ms
```

PostgreSQL از روش `Sequential Scan` استفاده کرده است. در این روش، رکوردهای جدول به‌صورت متوالی بررسی می‌شوند تا رکوردهای مطابق با شرایط `WHERE` پیدا شوند.

از آنجا که هیچ رکوردی با شرایط این کوئری مطابقت نداشته است، هر ۱۰۱ رکورد پس از بررسی کنار گذاشته شده‌اند.

سپس PostgreSQL عملیات مرتب‌سازی را با الگوریتم `quicksort` انجام داده است.

## ۴. نتایج با ایندکس

در مرحله دوم، ایندکس ترکیبی زیر دوباره ایجاد شد:

```sql
CREATE INDEX tasks_store_id_due_at_index
ON tasks (store_id, due_at);
```

سپس همان کوئری مجدداً اجرا شد.

خلاصه خروجی:

```text
Sort
  Sort Key: due_at
  Sort Method: quicksort
  Memory: 25kB
  Buffers: shared hit=4
  -> Seq Scan on tasks
       Filter: ((store_id = 1) AND (due_at < now()))
       Rows Removed by Filter: 101
       Buffers: shared hit=4

Planning Time: 0.159 ms
Execution Time: 0.060 ms
```

با وجود ایجاد ایندکس، PostgreSQL همچنان از `Sequential Scan` استفاده کرده است.

این رفتار غیرعادی نیست. با توجه به تعداد کم رکوردهای جدول، اسکن کامل جدول می‌تواند برای PostgreSQL ارزان‌تر از استفاده از ایندکس باشد.

بنابراین، وجود ایندکس الزاماً به معنی استفاده PostgreSQL از آن در هر کوئری نیست؛ انتخاب روش اجرا بر اساس تخمین هزینه انجام می‌شود.

## ۵. مقایسه نتایج

| معیار | بدون ایندکس | با ایندکس |
|---|---:|---:|
| Scan Type | Sequential Scan | Sequential Scan |
| Planning Time | 1.046 ms | 0.159 ms |
| Execution Time | 0.036 ms | 0.060 ms |
| Shared Buffers Hit | 4 | 4 |
| تعداد رکوردهای بررسی‌شده | 101 | 101 |
| تعداد رکوردهای خروجی | 0 | 0 |

### تحلیل

در هر دو حالت، PostgreSQL از `Sequential Scan` استفاده کرده و تمام ۱۰۱ رکورد جدول را بررسی کرده است.

همچنین تعداد صفحات حافظه مورد استفاده در هر دو اجرا برابر بوده است.

زمان اجرای ثبت‌شده در حالت بدون ایندکس کمتر از حالت دارای ایندکس بوده است؛ بنابراین این آزمایش هیچ بهبود عملکردی ناشی از ایندکس را نشان نمی‌دهد.

اختلاف بسیار کوچک زمان‌ها را نمی‌توان به‌عنوان برتری قطعی یکی از دو حالت در نظر گرفت؛ زیرا عواملی مانند وضعیت Cache، بار سیستم و سربار اندازه‌گیری می‌توانند روی این مقادیر تأثیر بگذارند.

## ۶. محدودیت‌های آزمایش

این آزمایش با محدودیت‌های زیر انجام شده است:

- جدول `tasks` تنها ۱۰۱ رکورد داشته است.
- کوئری در هر دو حالت صفر رکورد برگردانده است.
- PostgreSQL در هر دو حالت از `Sequential Scan` استفاده کرده است.
- زمان‌های اندازه‌گیری‌شده بسیار کوتاه هستند و برای نتیجه‌گیری درباره عملکرد در مقیاس بزرگ کافی نیستند.
- این آزمایش روی یک پایگاه داده توسعه انجام شده و جایگزین Benchmark با داده‌های حجیم و الگوهای واقعی بار کاری نیست.

## ۷. نتیجه‌گیری

این آزمایش نشان داد که PostgreSQL همیشه از ایندکس‌های موجود استفاده نمی‌کند و انتخاب Execution Plan به تخمین هزینه اجرای روش‌های مختلف بستگی دارد.

در جدول کوچکی با ۱۰۱ رکورد، استفاده از `Sequential Scan` در حضور ایندکس نیز می‌تواند انتخاب بهینه‌تری باشد.

ایندکس ترکیبی `(store_id, due_at)` همچنان برای کوئری‌هایی که بر اساس فروشگاه و زمان سررسید فیلتر می‌کنند، یک گزینه مناسب طراحی است؛ اما اثبات میزان تأثیر آن بر عملکرد، به آزمایش با حجم داده بیشتر و شرایط نزدیک‌تر به محیط واقعی نیاز دارد.

**نکته:** نتایج این آزمایش صرفاً برای مستندسازی و آشنایی با تحلیل Execution Plan ثبت شده‌اند و نباید به‌عنوان اثبات افزایش سرعت کوئری در محیط عملیاتی تفسیر شوند.
