# راهنمای اجرای دمو پروژه Kasbify

## ۱. معرفی پروژه

**Kasbify** یک RESTful API برای مدیریت وظایف (Task Management) است که با استفاده از Laravel و PostgreSQL توسعه داده شده است.

در این پروژه، کاربران می‌توانند عضو فروشگاه‌های مختلف باشند و بر اساس نقش خود در هر فروشگاه، عملیات مشخصی را انجام دهند.

دو نقش اصلی سیستم عبارت‌اند از:

- **Manager:** مدیر فروشگاه که به تمام وظایف فروشگاه دسترسی دارد و می‌تواند وظایف را ایجاد، ویرایش، تخصیص و مدیریت کند.
- **Staff:** کارمند فروشگاه که وظایف تخصیص‌یافته به خودش را مشاهده و مدیریت می‌کند.

هدف این راهنما، نمایش قابلیت‌های اصلی API و بررسی عملکرد آن از طریق Postman است.

## ۲. پیش‌نیازهای اجرای پروژه

قبل از شروع دمو، موارد زیر باید آماده باشند:

1. نصب و راه‌اندازی PHP و Composer
2. نصب و راه‌اندازی PostgreSQL
3. نصب وابستگی‌های پروژه با دستور `composer install`
4. تنظیم فایل `.env` و اتصال صحیح به دیتابیس
5. اجرای Migrationها و Seedها
6. اجرای سرور Laravel
7. وارد کردن Postman Collection و Environment ارائه‌شده

برای اجرای سرور توسعه Laravel از دستور زیر استفاده کنید:

```bash
php artisan serve
```

آدرس پایه API:

```text
http://127.0.0.1:8000/api/v1
```

## ۳. اطلاعات حساب‌های آزمایشی

برای اجرای دمو، دو حساب کاربری از پیش تعریف‌شده در Seed دیتابیس در نظر گرفته شده‌اند.

| نقش | ایمیل | رمز عبور |
|---|---|---|
| Manager | Alice@example.com | password123 |
| Staff | bob@example.com | password234 |

این اطلاعات صرفاً برای محیط آزمایشی و اجرای دمو هستند و نباید در محیط Production استفاده شوند.

## ۴. آماده‌سازی Postman

دو فایل زیر را در Postman وارد کنید:

- `Kasbify.postman_collection.json`
- `Kasbify.postman_environment.json`

مراحل آماده‌سازی:

1. از قسمت Import در Postman، هر دو فایل را وارد کنید.
2. از قسمت Environment، محیط `Kasbify Local` را انتخاب کنید.
3. در Environment، مقادیر زیر را تنظیم کنید:

| Variable | Value |
|---|---|
| `base_url` | `http://127.0.0.1:8000/api/v1` |
| `manager_email` | `Alice@example.com` |
| `manager_password` | `password123` |
| `staff_email` | `bob@example.com` |
| `staff_password` | `password234` |

سایر متغیرها مانند Tokenها و شناسه‌های Store و Task به‌صورت خودکار توسط اسکریپت‌های Collection مقداردهی می‌شوند.

## ۵. سناریوی اجرای دمو

### مرحله اول: احراز هویت مدیر

ابتدا وارد پوشه `01 - Authentication` شوید.

درخواست `Login - Manager` را اجرا کنید.

در صورت موفقیت، پاسخ شامل اطلاعات کاربر و Token احراز هویت خواهد بود. Token به‌صورت خودکار در متغیر `manager_token` ذخیره می‌شود.

سپس دو درخواست زیر را اجرا کنید:

- `Get Current User - Manager`: دریافت اطلاعات کاربر احراز هویت‌شده
- `Get My Stores - Manager`: دریافت فروشگاه‌هایی که کاربر عضو آن‌هاست

در این مرحله، شناسه اولین فروشگاه در متغیر `store_id` ذخیره می‌شود.

### مرحله دوم: بررسی دسترسی‌های مدیر

به پوشه `02 - Store Management (Manager)` بروید.

**۱. List Store Members**

این درخواست فهرست اعضای فروشگاه را نمایش می‌دهد. اطلاعات هر عضو شامل شناسه، نام، ایمیل و نقش او است.

شناسه یکی از اعضای دارای نقش Staff به‌صورت خودکار در متغیر `assigned_user_id` ذخیره می‌شود.

**۲. Get Task Summary**

این درخواست خلاصه‌ای از وضعیت وظایف فروشگاه را برمی‌گرداند؛ از جمله:

- تعداد کل وظایف
- تعداد وظایف در هر وضعیت
- تعداد وظایف عقب‌افتاده (Overdue)

این قابلیت فقط برای مدیر فروشگاه در دسترس است.

### مرحله سوم: مدیریت وظایف توسط مدیر

به پوشه `03 - Tasks (Manager)` بروید.

**۱. Create Task**

یک وظیفه جدید در فروشگاه ایجاد کنید.

اطلاعات نمونه شامل عنوان، توضیحات و اولویت وظیفه است. پس از ایجاد موفق، شناسه Task در متغیر `task_id` ذخیره می‌شود.

پاسخ موفق این درخواست دارای کد وضعیت HTTP `201 Created` است.

**۲. List Tasks**

فهرست وظایف فروشگاه را دریافت کنید.

**۳. List Tasks - Filtered**

این درخواست نمونه‌ای از قابلیت فیلترگذاری را نمایش می‌دهد. API از فیلترهایی مانند موارد زیر پشتیبانی می‌کند:

- وضعیت وظیفه (`status`)
- اولویت (`priority`)
- کاربر تخصیص‌یافته (`assigned_to`)
- عقب‌افتاده بودن (`overdue`)
- جست‌وجوی متنی (`q`)

همچنین نتایج از صفحه‌بندی (Pagination) پشتیبانی می‌کنند.

**۴. Get Task Details**

جزئیات وظیفه ایجادشده را با استفاده از شناسه آن دریافت کنید.

**۵. Update Task Details**

اطلاعات قابل ویرایش وظیفه مانند عنوان، توضیحات، اولویت و زمان سررسید را تغییر دهید.

**۶. Assign Task to Staff**

وظیفه را به کارمند فروشگاه تخصیص دهید.

در این درخواست، شناسه کارمند از متغیر `assigned_user_id` خوانده می‌شود. سیستم بررسی می‌کند که کاربر انتخاب‌شده عضو همان فروشگاه باشد.

### مرحله چهارم: بررسی اعتبارسنجی و محدودیت‌های تجاری

در پوشه `04 - Optional Negative Tests` دو درخواست برای نمایش رفتار سیستم در شرایط نامعتبر قرار داده شده است.

**۱. Invalid Status Transition**

این درخواست تلاش می‌کند وضعیت یک وظیفه را مستقیماً از `todo` به `done` تغییر دهد.

چون این انتقال در منطق تجاری سیستم مجاز نیست، API باید پاسخ `409 Conflict` برگرداند.

**۲. Unknown Fields Validation**

در این درخواست، یک فیلد غیرمجاز به اطلاعات ورودی اضافه می‌شود.

سیستم باید درخواست را با پاسخ `422 Unprocessable Entity` رد کند.

این آزمایش نشان می‌دهد که اعتبارسنجی ورودی‌ها فقط به بررسی مقادیر محدود نیست و فیلدهای ناشناخته نیز کنترل می‌شوند.

### مرحله پنجم: ورود کارمند و مدیریت وظیفه

به پوشه `05 - Tasks (Staff)` بروید.

**۱. Login - Staff**

با حساب کاربری کارمند وارد سیستم شوید.

پس از ورود موفق، Token کارمند در متغیر `staff_token` ذخیره می‌شود.

**۲. Get Current User - Staff**

اطلاعات کاربر احراز هویت‌شده را دریافت کنید.

**۳. Get Assigned Task**

کارمند می‌تواند وظیفه تخصیص‌یافته به خودش را مشاهده کند.

**۴. Start Task**

کارمند وضعیت وظیفه را از `todo` به `in_progress` تغییر می‌دهد.

**۵. Complete Task**

پس از شروع وظیفه، کارمند می‌تواند وضعیت آن را به `done` تغییر دهد.

در این مرحله، زمان تکمیل وظیفه (`completed_at`) نیز توسط سیستم ثبت می‌شود.

### مرحله ششم: ثبت و مشاهده نظرات

به پوشه `06 - Comments (Staff)` بروید.

**۱. Add Comment**

کارمند می‌تواند یک نظر جدید برای وظیفه ثبت کند.

متن نظر باید بین ۱ تا ۲۰۰۰ کاراکتر باشد.

**۲. List Comments**

فهرست نظرات ثبت‌شده برای وظیفه را دریافت کنید.

نظرات پس از ثبت، در طراحی API به‌صورت append-only در نظر گرفته شده‌اند؛ یعنی endpoint برای ویرایش یا حذف آن‌ها ارائه نشده است.

### مرحله هفتم: مشاهده تاریخچه تغییرات

به پوشه `07 - Task History` بروید.

**List Task Events**

این درخواست تاریخچه رویدادهای ثبت‌شده برای وظیفه را نمایش می‌دهد.

برای مثال، تغییر وضعیت وظیفه یا تغییر اطلاعات آن می‌تواند یک Event ایجاد کند.

هر رویداد شامل اطلاعاتی مانند موارد زیر است:

- نوع رویداد (`event_type`)
- کاربر انجام‌دهنده عملیات (`actor_id`)
- تغییرات قبل و بعد (`changes`)
- زمان ثبت رویداد (`created_at`)

این قابلیت امکان پیگیری تغییرات انجام‌شده روی وظایف را فراهم می‌کند.

## ۶. نکات فنی قابل توجه در دمو

در کنار قابلیت‌های اصلی، پروژه چند ویژگی مهم در سطح امنیت و یکپارچگی داده‌ها دارد:

- **Authentication:** احراز هویت با Laravel Sanctum و استفاده از Bearer Token
- **Authorization:** کنترل دسترسی بر اساس نقش کاربر در هر فروشگاه
- **Store Isolation:** جلوگیری از دسترسی کاربران به اطلاعات فروشگاه‌هایی که عضو آن‌ها نیستند
- **Validation:** اعتبارسنجی داده‌های ورودی با استفاده از Form Requestها
- **Database Integrity:** استفاده از Foreign Keyها، Composite Foreign Keyها و Check Constraintها برای حفظ صحت داده‌ها
- **Transactions:** استفاده از تراکنش و قفل‌گذاری رکوردها در عملیات حساس مانند تغییر وضعیت و تخصیص وظیفه
- **Event Logging:** ثبت تغییرات مهم برای ایجاد تاریخچه قابل پیگیری
- **Rate Limiting:** محدودسازی تعداد تلاش‌های ناموفق ورود به سیستم
- **Pagination & Filtering:** پشتیبانی از صفحه‌بندی و فیلترگذاری در فهرست وظایف

## ۷. نتیجه‌گیری

در این دمو، چرخه اصلی مدیریت وظایف در Kasbify از طریق Postman بررسی می‌شود:

1. ورود مدیر و دریافت اطلاعات فروشگاه
2. مشاهده اعضا و آمار وظایف
3. ایجاد و ویرایش وظیفه
4. تخصیص وظیفه به کارمند
5. بررسی اعتبارسنجی و انتقال وضعیت‌های غیرمجاز
6. ورود کارمند و شروع و تکمیل وظیفه
7. ثبت نظر و مشاهده تاریخچه تغییرات

این سناریو علاوه بر نمایش endpointهای اصلی، نحوه اعمال قوانین تجاری، کنترل دسترسی و حفظ یکپارچگی داده‌ها را نیز نشان می‌دهد.
